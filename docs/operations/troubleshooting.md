# Troubleshooting & Incident Response

Combines the debug playbook and error taxonomy into a single escalation manual.

## Debug Playbook

This playbook lists common Tri-ARC failure patterns, diagnostics, and remediation steps. Use it alongside runtime telemetry and module-specific logs to resolve issues quickly during development or evaluation.

## Tools And Logs
- **Runtime log** (`logs/runtime.log`): Scheduler allocations, module start/stop events.
- **Metrics stream** (`metrics.jsonl`): Per-task timings, module success rates, SMT statistics.
- **Module lifecycle events** (`metrics.jsonl` entries with `event` = `module_start|module_stop|module_error`): Generated by the shared `SolverModule` base; correlate with runtime log entries to trace orchestration issues.
- **Profiler traces** (`profiles/`): Torch profiler exports, Nsight GPU samples.
- **SMT dumps** (`logs/smt/`): Constraint snapshots and solver outcomes.
- **Debug CLI** (`python tools/debug.py`): Inspect module state, replay tasks, view cached artefacts.
- **Frontier inspector** (`python tools/inspect_frontier.py --log logs/symbolic/symbolic_frontier.log --task <id>`): Summarise frontier events and recent snapshots for a single task.
- **Symbolic replay** (`python tools/replay_symbolic.py --task <id> --frontier-log logs/symbolic/symbolic_frontier.log --egraph-history logs/symbolic/egraph/egraph_history.jsonl`): Step through search timelines and rewrite histories.
- **Arbitrator inspector** (`python tools/inspect_arbitrator.py --task <id>`): Replay decision rationale, candidate scores, and regenerate pass@2 payloads.

## Issue Matrix
| Symptom | Likely cause | Diagnosis steps | Fix |
|---------|--------------|-----------------|-----|
| Symbolic solver times out early | Rewrite explosion or mis-scored heuristics | Check `symbolic_frontier.log` for frontier size; inspect scheduler allocation | Tighten beam width via `docs/policies/orchestration.md`, prune rewrite agenda |
| TTT outputs inconsistent grids | Overfitting or gradient instability | Review loss curves in `metrics.jsonl`; run `tools/plot_ttt.py` | Reduce learning rate, increase auxiliary loss weights, reset adapters |
| LLM candidates fail SMT en masse | Prompt drift or quantisation artifacts | Inspect `logs/smt/failed/*.json`; run `tools/llm_replay.py` with higher precision | Refresh prompt templates, lower temperature, regenerate quantised weights |
| SMT solver returns unknown frequently | Constraint blow-up or unsupported primitives | Examine solver timeout entries; verify DSL primitive coverage | Simplify candidate programs, add missing primitive semantics in `docs/reference/dsl_reference.md` |
| Arbitrator emits duplicate answers | Diversity logic disabled or insufficient candidates | Check arbitrator decision logs; ensure score diversity thresholds | Raise LLM candidate count, adjust diversity bonus rules in `docs/policies/orchestration.md` |
| Arbitrator falls back too often | Upstream verifiers rejecting viable candidates or low priors | Inspect `logs/arbitrator/verification/*.json` for mismatches; review `metrics.jsonl` fallback rate | Improve module priors, fix module verification failures, widen diversity gap cautiously |
| Scheduler overruns 12-hour budget | Inaccurate runtime estimates | Compare projected vs actual runtimes in `metrics.jsonl`; inspect per-task budgets | Update scheduler lookup tables, throttle lower-priority lanes, enable early exits |

## Arbitrator Diagnostics
- Read decision snapshots under `logs/arbitrator/decisions/<task>.json` to view emitted answers, rationale strings, and provenance.
- Verification transcripts reside in `logs/arbitrator/verification/`; mismatches include counterexamples and execution error metadata for rapid triage.
- Daily summaries (`reports/arbitration_summary_<date>.md`) capture per-task notes, while health dashboards (`reports/arbitrator_health_<date>.md`) aggregate fallback usage, low-confidence counts, and latency trends.
- Use `python tools/inspect_arbitrator.py --task <id> --show-traces` to correlate decision records with verification logs, or `--regenerate` to rebuild `outputs/pass2.json` from archived decisions after incident triage.

## Workflow For Task Failures
1. **Capture context**: Record task ID, module provenance, and elapsed time.
2. **Replay**: Run `python tools/replay_task.py --task <id> --module <lane>` to reproduce the issue with verbose logging.
3. **Inspect artefacts**:
   - Symbolic: examine generated programs under `outputs/symbolic/`.
   - TTT: review saved checkpoints in `cache/ttt/`.
   - LLM: open the prompt-response transcript in `logs/llm/`.
   - Cross-check module telemetry in `metrics.jsonl` for matching `module_start`/`module_stop` events and durations.
4. **Fix and validate**: Apply module-specific adjustments, rerun the replay, and confirm the arbitrator now selects a correct candidate.
5. **Document**: Update this playbook or module docs if new error patterns emerge.

## DSL Verification Workflow
1. **Quick health check**: run `python scripts/run_dsl.py --fixtures fixtures/dsl/spec_examples --benchmark-report reports/dsl_benchmarks_<date>.md` to execute the canonical suite, refresh benchmarks, and emit JSONL logs under `logs/verification/`.
2. **Drill into failures**: inspect the generated log (`logs/verification/verification_<timestamp>.jsonl`) for grid diffs, value mismatches, or validation errors; rerun the specific case using `scripts/run_dsl.py --fixtures <path/to/fixture> --quiet`.
3. **Spec alignment**: reconcile failures against `docs/reference/dsl_reference.md`; patch primitive behaviour in `arc/symbolic/dsl/runtime/primitives.py` and add regression coverage in `tests/dsl/`.
4. **Downstream readiness**: downstream modules should call `arc/symbolic/interpreter_adapter.py` to execute programs, ensuring validation happens consistently across CI and local runs.

## Profiling Guidelines
- Run `python tools/profile.py --module ttt --duration 60` to sample GPU utilisation.
- Use Nsight CLI (`nsys profile python scripts/run_eval.py --task <id>`) for deep dives; limit sessions to short intervals to preserve runtime budget.
- Summarise profiler findings in `reports/perf_notes.md` for future reference.

## Logging Hygiene
- Rotate logs daily or when size exceeds 2 GB to prevent disk saturation.
- Compress archived logs (`xz` or `gzip`) before long-term storage.
- Ensure solver dumps are anonymised before sharing outside the team.

## Escalation
- If repeated failures persist, open an incident entry in the project tracker with task IDs, logs, and reproduction steps.
- Tag responsible module owners and assign follow-up timelines.
- Merge remediation changes only after regression suites covering ARC-Forge tasks pass.

## Error Taxonomy

Tri-ARC logs every unsolved or low-confidence task using a shared taxonomy so ablations, regressions, and ARC-Forge synthesis can target the right failure modes. Annotators should apply the criteria below consistently; ambiguous cases receive multiple tags ordered by prevalence.

## Tagging Guidelines
- **Granularity**: Assign at least one high-level category (Symbolic, TTT, LLM, Cross-Module, Infrastructure). Add sub-tags when evidence is clear.
- **Evidence first**: Use module logs, SMT traces, and grid diffs to justify each label. Avoid speculation.
- **Order**: List tags from most to least causal. For example, `Symbolic:RuleInteraction`, `CrossModule:Arbitration`.
- **Severity**: Mark `Critical` when the failure blocks evaluation (no output, crash). Otherwise mark `Major` (incorrect output) or `Minor` (correct but slow/low confidence).
- **Example snapshots**: Save before/after grids or program snippets in `reports/errors/<task_id>/`.

## Category Definitions And Examples

### Symbolic
- **RuleInterpretation**: Synthesised program misses the underlying rule (e.g., misidentifies the target object).  
  *Example*: Program paints the second-largest object instead of the largest; counterexample shows incorrect region mask.*
- **RuleInteraction**: Partial rules conflict or stack incorrectly (e.g., symmetry plus recolour).  
  *Example*: E-graph rewrite drops an order constraint, leading to swapped operations.*
- **SearchTimeout**: Beam search exhausts budget before finding a consistent program.
- **LibraryGap**: Required primitive absent; solver attempts to emulate with verbose alternative and fails.

### Test-Time Training (TTT)
- **OverfitSupport**: Adapted model matches support examples but diverges on test grid; loss spikes on held-out validation sample.
- **GradientDivergence**: Training blows up (NaNs, exploding gradients) causing reset.
- **Underadaptation**: Early stopping triggers before loss plateau due to conservative scheduler settings.

### LLM
- **PromptDrift**: Generated explanation misreads task schema; SMT rejects all candidates.
- **SyntaxError**: Output malformed (unclosed parentheses, invalid DSL tokens).
- **HallucinatedPrimitive**: References DSL primitive that does not exist in `docs/reference/dsl_reference.md`.
- **LowConfidence**: All candidates pass SMT but arbitrator score below threshold due to high complexity/logprob penalty.

### Cross-Module
- **ArbitrationConflict**: Two high-scoring candidates disagree; tie-breaker selects wrong answer.
- **SchedulerBudget**: Budgets misallocated, starving the successful lane (document relevant metrics from `docs/policies/orchestration.md`).
- **SMTBottleneck**: Verifier backlog prevents timely evaluation, causing modules to timeout.

### Infrastructure
- **IOFailure**: Dataset read/write issues, missing cache files, corrupted JSON.
- **OOM**: GPU or CPU memory exhaustion leading to aborted run (see `docs/handbook/evaluation_suite.md` for mitigation).
- **TimeoutGlobal**: Run exceeds 12-hour limit, leaving tasks unsolved.

## Annotation Template
```
task_id: XXXXX
severity: Major
tags:
  - Symbolic:RuleInteraction
  - CrossModule:Arbitration
evidence:
  - symbolic_log: reports/program_XXXXX.dsl
  - arbitrator_score: primary=0.58 secondary=0.54
notes: "Symbolic program applied reflect before recolor; secondary TTT output correct but deprioritised."
actions:
  - investigate e-graph rewrite priority
  - adjust arbitrator diversity bonus
```

## Usage In Experiments
- Regression suites consume tags to ensure previously fixed categories remain solved.
- Ablations (see `docs/handbook/evaluation_suite.md`) group errors by category to explain performance deltas.
- ARC-Forge prioritises generating tasks from categories with the highest unresolved counts.
